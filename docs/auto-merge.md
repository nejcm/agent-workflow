# Auto-merge

`autoMerge` (requested in the repo's [`.tender/config.yaml`](config.md#repo-config), capped by the repo's `autoMerge` in `tender.json`) lets `tender` merge a ticket's PR; the prompt forbids the agent to merge. That is a prompt rule, not a boundary: the sandbox's GitHub token can reach `/repos/**` and `/graphql` (`gh pr create` needs GraphQL, and nono filters only method + path, not the mutation), so a prompt-injected agent can still `gh pr merge` or push to `baseBranch` itself, even with `autoMerge: "off"` or `no-automerge`. The real boundary is GitHub branch protection on `baseBranch` (required PR, required status checks); enable it. On every poll, for each in-review ticket with an open PR on `agent/<ID>`, `tender` reads `gh pr view --json …` and decides:

- `off` (default): never merges.
- `all`: merges when the PR is open, not a draft, from this repo (not a fork), targets `baseBranch`, has no conflicts, no review decision "changes requested" or "review required", is not blocked by branch protection (`mergeStateStatus` `BLOCKED`), no check failed or pending (zero checks is fine once the PR was last updated 2 minutes ago, so CI has time to register a check after a push), neither the PR nor the ticket has the label `no-automerge`, no changed file's path, or old path for a rename, matches a critical path, no added line holds an escape hatch (below), and the [verify contract](#verify-contract) passed at the PR's head; without a contract only a small change (below) merges, even in `all`.
- `shadow`: decides exactly like `intelligent` but never merges: it posts one `tender: would auto-merge: <reason>` (or `tender: not auto-merged: <reason>`) comment per head SHA and verdict (a check re-run or a removed label that flips it comments again, once per verdict) and never merges, though the ticket can still move to [Ready to merge](lifecycle.md#ready-to-merge). Use it to see what `intelligent` would do before turning it on; [`tender stats`](stats.md#trust-signals) counts how often it agreed with what you then did.
- `intelligent`: the same as `all`, plus gates `tender` computes from the PR itself. Never merged: an existing test file that loses lines, is deleted, is renamed (from or to a test path) or is modified with 0 lines either way, as a binary fixture or a mode-only change is (adding test files or only adding lines to one is fine); or a large change. Size is additions + deletions and changed files: small ≤ 150 lines and ≤ 5 files, medium ≤ 500 and ≤ 15, else large. Small needs nothing more (zero checks is fine, as above). Medium also needs at least one check that succeeded (skipped or neutral ones don't count), and a valid `.tender/run/merge.json` from the agent with `confidence: "high"`, `critical: false` and `reviewed: true` (a model of a different family reviewed the final diff; missing or `false` counts like `confidence: "low"` here).

## Verify contract

`.tender/verify.yaml` lists the commands that stand in for "the tests pass": `checks`, 1 to 20 of `{ name, run, timeout?, proof? }` (`name` `[a-z0-9-]`, unique; `run` a `sh -c` command line; `timeout` seconds, default 600, at most 1800; `proof` globs ending in `.png`, `.gif`, `.jpg`, `.jpeg`, `.webp`, `.svg`, `.mp4`, `.mov` or `.webm`, parsed but not yet collected), and `maxRounds` (default 2). Like the rest of `.tender/`, it is read from `origin/<baseBranch>` of the base clone, never from the PR, and an invalid file fails the whole config (`tender check` validates it). Once the ticket is done for now (the condition [Ready to merge](lifecycle.md#ready-to-merge) waits for: tmux quiet for 5 minutes, or the window confirmed gone), `tender` fetches `refs/pull/<n>/head` into the base clone, starts only if that is the head it judged, and runs the checks in order in the background, sandboxed (see [sandbox](sandbox.md#verify)), on a detached checkout in `<ID>.verify`. One run at a time per workspace; the poll never waits for it. The result is kept in `<ID>.verified` for that head and the file's sha256, so a push or a changed contract needs a new run. A run that ends without a result (killed, out of memory or past its deadline) is recorded as a failure of `(verifier)` rather than run again. To rerun a head whose failure was flaky, delete `<ID>.verified` next to the worktree. With a contract, `intelligent` and `all` merge only on a pass for the current head and contract, a fail holds the PR back (`verify failed: <check>`) and goes to the agent as [feedback](lifecycle.md#pr-feedback), and anything else waits; a `.tender/` that cannot be read holds merges, as always. The contract is the one at `origin/<baseBranch>` as this poll fetched it (a PR's `baseRefOid` is only the base at its last sync), and right before merging `tender` checks with `git ls-remote` that the branch has not moved since; if it has, the merge waits for the next poll. Without one, medium and large changes never auto-merge. The contract protects which commands run, not what they do: the scripts they call are head code the agent can change, so keep scripts that must not change under `.tender/checks/` (critical, so a PR touching them never auto-merges) and call them from `run`. The run has no network: dependencies must be in the clone or install offline from the read-only `~/.bun`, `~/.npm` and mise installs (`~/.local/share/mise`).

Changed files come from `gh api --paginate repos/<owner>/<name>/pulls/<n>/files` (not `gh pr view --json files`, which lacks a rename's old path and stops at 100 files), fetched only when every other gate would let the PR merge; a list whose length differs from the PR's `changedFiles` holds it back.

**Trust per path.** The repo's `trust` rules set a mode per file: a changed file (and a rename's old path) takes the mode of the first rule whose globs match it, else the repo's `autoMerge`. The PR's mode is the lowest across its files, capped by the host's `autoMerge`, so a rule can lift docs to `all` above the repo's `autoMerge` but never above the host's ceiling, and one file under an `off` rule holds back the whole PR (`tender: not auto-merged: trust sets <path> to off`). Critical paths still block in every mode. Until the files are fetched, the other gates are judged at the highest mode the rules allow.

**Escape hatches.** When the file gates pass, `tender` reads the PR's diff with `gh api repos/<owner>/<name>/compare/<base SHA>...<head SHA>` (the diff media type, through `head -c`, so at most 2 MB is ever buffered), pinned to both SHAs. A diff over 2 MB is not auto-merged. Only added lines count, found by the hunk counts, so removed and context lines are ignored. Built-in patterns. Comment directives, ignoring case, with any run of whitespace where a pattern has a space or around its punctuation, and a pattern that starts with a letter only at a word start: `eslint-disable`, `@ts-ignore`, `@ts-expect-error`, `@ts-nocheck`, `# type: ignore`, `# noqa`, `ruff: noqa`, `flake8: noqa`, `# mypy: ignore-errors`, `# pyright: ignore`, `# pylint: disable`, `# rubocop:disable`, `//nolint`, `lint:ignore`, `lint:file-ignore`, `biome-ignore`, `oxlint-disable`, `deno-lint-ignore`, `shellcheck disable`, `#[allow(`, `#![allow(`, `#[expect(`, `allow(` inside `#[cfg_attr(`, `@SuppressWarnings`, `@Suppress`, `@file:Suppress`, `SuppressMessage(`, `#pragma warning disable` (also `#pragma warning(disable`), `as any` and `as unknown as` (as words), and coverage exclusions (`# pragma: no cover`, `# pragma: no branch`, `istanbul ignore`, `c8 ignore`, `v8 ignore`). The patterns run in a worker cut off after 5 seconds, so a backtracking regex (even `\s+$` on a long line) cannot stall the poll; a cut-off is not auto-merged either. Only the result is kept, per PR, until the base SHA, head SHA or patterns change; the merge is also dropped until the next poll if the base moves between the decision and the pre-merge view. The first match gives `tender: not auto-merged: adds escape hatch "<pattern>" in <file>`. It applies to `all` and `intelligent`; `shadow` reports it.

The agent writes `.tender/run/merge.json` (`{ "confidence": "high|medium|low", "critical", "reviewed", "reviewer"?, "reason" }`, max 4 KiB, read like the phases file: no symlinks, regular file only) just before opening the PR. Ticket text can steer the agent, so the file is untrusted: it can only hold a merge back (`critical: true` or `confidence: "low"` blocks any size; missing or invalid blocks medium), never let one through. Pending checks, unknown mergeability, or zero checks on a PR updated under 2 minutes ago (`updatedAt`: any push, comment or label resets it) wait silently. A PR whose `reviewDecision` is `REVIEW_REQUIRED` is held with a reason, pending checks or not; one that branch protection blocks (`BLOCKED`) is held once nothing waits. Either is held instead of failing `gh pr merge` every poll, and, unless trust resolves its files to `off` (fetching them for this), is kept out of or moved back from [Ready to merge](lifecycle.md#ready-to-merge). A merge is `gh pr merge <n> --squash --delete-branch --match-head-commit <sha>` (never `--admin`), so a push after the decision makes it fail. Right before merging `tender` views the PR again and re-runs every gate; if the head moved, it drops `<ID>.merge` and decides on the new head next poll. A failed merge is logged and retried next poll, and so is a PR not yet `MERGED` after the command. On a base branch with a merge queue `gh` refuses `--delete-branch`, so `tender` retries without it, which adds the PR to the queue (the branch is then deleted only by the repo's auto-delete setting); while queued it stays open, so each poll logs it as not yet merged, and the queue's merge is then recorded like a merge by hand. A ticket parked after that does not leave the queue. After a merge `tender` comments once, closes the GitHub issue / moves the Linear ticket to the first `done` state, and cleanup follows. A PR found merged on a later poll (also by hand) moves the ticket the same way if it is from this repo and targets `baseBranch`, which retries a failed close; this also runs on a parked ticket, which otherwise gets no merge and no comment. A PR that is not merged gets one `tender: not auto-merged: <reason>` comment per head SHA and reason (an open PR whose blocker clears and another refuses gets one more; `shadow` likewise comments once per verdict), recorded in `<ID>.merge` next to the worktree; it is re-evaluated every poll, so a re-run check or a removed label still lets it merge without a new commit.
